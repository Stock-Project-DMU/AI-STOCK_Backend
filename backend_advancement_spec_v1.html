백엔드 고도화 명세서 — 완료 기능 재검토·개선 후보

backend_8week_plan_v7에서 담당자별로 완료했던 기능(A: 실시간·AI, B: 주문·계좌, C: 인증·조회·관리자)을 대상으로, 같은 기능 영역을 다시 살펴 고도화할 지점을 정리한 문서입니다. 아래 항목들은 확정된 작업 지시가 아니라 코드 리뷰로 도출한 후보입니다 — 우선순위·착수 여부·구현 방식은 팀 회의에서 확정합니다. 착수 전 CLAUDE.md·NAMING.md·schema.sql 최신본을 항상 먼저 확인하세요.

이 문서가 다루는 범위

팀원 A는 이번 명세서에서 LS증권 연동 아키텍처 변경 하나를 다룹니다 — 별도 로컬 시세 서버가 LS증권 실시간 시세를 수신·가공해 파일로 저장하고, 이 Spring Boot 프로젝트는 그 파일을 읽는 구조로 바꿉니다. 후보는 하나지만 선행조건이 있는 A-1~A-7 단계로 쪼개 아래 보드에 담았습니다. 팀원 B·C는 이미 완료된 주문·계좌 / 인증·조회·관리자 도메인 코드를 리뷰해서 나온 개선 후보 6개씩을 다룹니다.

A-1~A-7 단계가 공통으로 참조하는 세부 규칙(파일 조회 키 규칙, 이름 후보, 범위 밖 사항)은 문서 하단 "LS증권 최신화 아키텍처" 섹션에 정리했습니다. 파일 조회 키 규칙과 이름 후보는 아직 미확정 제안이며, 로컬 시세 서버를 실제로 만드는 쪽과 합의한 뒤 최종 확정합니다.

참고 문서: CLAUDE.md(코딩 규칙) · schema.sql(DB 설계) · redis-logic.md(Redis 키 설계) · KNOWN_ISSUES.md(기존에 알려진 미해결 이슈) · backend_8week_plan_v7.html(담당자·완료 이력). 이 명세서의 "위치" 필드는 코드 리뷰 시점 기준이며, 실제 착수 전에는 dev pull 후 라인 번호가 달라졌는지 다시 확인하세요.
아키텍처 변경구조 자체를 바꾸는 결정 기능 공백설계·화면은 있는데 구현이 비어있음 개선동작은 하지만 다듬을 지점 쉬움 보통 어려움
고도화 후보 — 담당자별
팀원 A실시간·AI 트랙
A-1 아키텍처 변경 코드 작업 아님
배경 확인 + 로컬 서버와 파일 조회 계약 확정
(팀 간 합의 — application.yml의 ls.* TR 코드 목록 기준)
현재 LsWebSocketClient만 ls.mode 조건이 걸려 있고, AiPlanningService가 쓰는 9개 LS REST 클라이언트(LsMarketDataApiClient 등, 25개 도구)는 ls.mode와 무관하게 항상 실제 LS API를 직접 호출한다 — dev/CI에서 ls.mode=mock이어도 AI 상담 도구 호출은 매번 진짜 LS API를 태우는 상태다. 로컬 시세 서버가 채워줄 파일 경로 규칙과 TR별 JSON 스키마(LS 실제 응답 outBlock과 동일 구조)를 로컬 서버 구현 측과 먼저 합의한다 — 그래야 이후 단계에서 기존 parseXxx() 파싱 코드를 그대로 재사용할 수 있다.
진행 방향(후보): 9개 클라이언트 전체를 한 번에 합의하기 어려우면 현재가(t1102)부터 우선 합의하고 착수 후 순차 확장.
A-2 아키텍처 변경 쉬움
ls.mode 설정 확장 + 토큰 발급 분기
application.yml / infra/ls/LsAccessTokenProvider
ls.mock-data-path(가칭) 프로퍼티를 기존 ls.* 패턴대로 추가하고, LsAccessTokenProvider.issueAccessToken()이 ls.mode=mock이면 실제 LS 인증서버 호출을 생략하고 더미 토큰을 반환하도록 수정한다. 이걸 빼먹으면 "파일만 읽는다"는 목표와 달리 매 호출마다 토큰 발급 API는 여전히 얻어맞는다.
진행 방향(후보): NAMING.md에 새 프로퍼티·클래스 이름을 먼저 등록한 뒤 진행(CLAUDE.md §11).
A-3 아키텍처 변경 보통
로컬 파일 리더 컴포넌트 신규 작성
infra/ls (신규 컴포넌트, 가칭 LsMockDataFileReader)
trCd + 요청 파라미터로 A-1에서 합의한 파일 경로를 만들고 JSON을 읽어 REST 응답과 동일한 Map<String, Object>로 반환한다. 파일이 없거나 파싱 실패 시 기존과 동일하게 CustomException(EXTERNAL_API_ERROR)를 던져, 각 클라이언트의 기존 실패 처리(catch → Optional.empty())가 그대로 동작하게 한다.
진행 방향(후보): 로컬 서버가 아직 없을 수 있으니 샘플 JSON 파일을 직접 만들어 단위 테스트로 먼저 검증.
A-4 아키텍처 변경 보통
LsApiClientSupport.call() 분기 연결 — 실제 전환 지점
infra/ls/LsApiClientSupport.call()
9개 클라이언트 전부가 거치는 이 한 지점에서 ls.mode에 따라 real→기존 REST 호출, mock→A-3 리더로 위임하도록 분기한다. 25개 도구 각각의 executeXxxLookup()· parseXxx()는 전혀 손대지 않는다 — 이 커밋부터 실제로 "로컬 파일 읽기"로 전환된다.
진행 방향(후보): A-2·A-3이 각각 검증된 뒤 마지막에 연결해 리스크를 낮춘다.
A-5 아키텍처 변경 보통
검증 — mock/real 모드 회귀 확인
9개 LsXxxApiClientTest, AiPlanningServiceTest
mock 모드에서 대표 도구(현재가·재무랭킹·테마정보 등 데이터 형태가 다른 것 위주) 응답을 확인하고, real 모드가 기존과 동일하게 실제 LS API를 계속 호출하는지(이번 변경이 real 모드 동작을 건드리지 않았는지) 회귀 확인한다.
진행 방향(후보): 기존 9개 클라이언트 테스트에 mock 케이스 추가.
A-6 아키텍처 변경 쉬움~보통

domain/ai/service/AiPlanningService.executeTool(), global/redis/RedisAiToolCacheService

진행 방향(후보): A-5 검증이 끝난 뒤 진행 — 안전망(캐시) 없이 먼저 빼면 파일 경로 문제가 검증 없이 바로 노출된다.

진행 방향(후보): 구현(A-2~A-6)이 끝난 뒤 마지막에 진행해 구현과 다르게 문서화되는 걸 방지.
팀원 B주문·계좌 트랙
B-1 개선 보통
사용자 주문 내역 API에 페이지네이션 없음
OrderController.getMyOrderHistory / OrderService (주문 목록 조회)
GET /api/orders가 계좌의 전체 주문 내역을 List로 한 번에 반환한다. 관리자용 AdminTradeController는 이미 Pageable을 쓰는데 사용자용은 없다. 모의투자 특성상 반복 매매가 잦아 누적될수록 응답 크기·조회 비용이 계속 커진다.
개선 방향(후보): AdminTradeController와 동일하게 Pageable + Page<OrderHistoryResponse>로 전환, Repository에 페이징 조회 메서드 추가.
B-2 개선 쉬움
체결 알림 메시지 생성 로직이 두 서비스에 완전히 중복
OrderService.buildExecutionMessage / OrderExecutionService.buildExecutionMessage
시장가 체결(OrderService)과 지정가 체결(OrderExecutionService)의 메시지 생성 코드가 완전히 동일하다. HoldingSettlementService처럼 이미 공용화한 선례가 있는데 이 메서드만 남아있다 — 문구 포맷을 바꿀 때 한 곳을 빠뜨릴 위험.
개선 방향(후보): Order의 정적 헬퍼 또는 공용 컴포넌트로 통합.
B-3 개선 보통
관리자 거래 목록 API에 필터링이 없음
AdminTradeController / AdminTradeService
GET /api/admin/trades는 페이지네이션만 있고 userId·종목코드· 주문상태·기간으로 좁혀볼 방법이 없다. 거래가 쌓이면 관리자가 특정 사용자·기간의 이상 거래를 찾기 어려워진다.
개선 방향(후보): 검색 조건 DTO + Repository 동적 조회(QueryDSL 또는 Specification) 추가.
B-4 기능 공백 쉬움~보통
관리자 계좌 목록/검색 API 자체가 없음
AdminAccountController (단건 조회·상태변경만 존재)
/api/admin/accounts에는 accountId 단건 조회·정지 처리만 있고 목록 조회 엔드포인트가 없다. "정지된 계좌 전체"를 보려면 AdminUserController의 사용자 상세를 거쳐야만 accountId를 알 수 있다.
개선 방향(후보): GET /api/admin/accounts?status=SUSPENDED 같은 목록 API(Pageable + status 필터) 추가.
B-5 개선 쉬움 (정책 판단 필요)
평단가 계산의 정수 나눗셈 누적 오차
Holding.increase()
totalCost / quantity가 추가매수마다 원 단위로 내림 처리된다(의도된 동작으로 주석 있음). 같은 종목을 여러 번 소액 분할매수하면 평단가가 실제보다 계속 낮게 드리프트할 수 있다. 모의투자라 실거래 정산 요건은 없어 영향은 낮음.
개선 방향(후보): 내림 대신 반올림 전환 검토 — 값의 의미가 바뀌는 변경이라 팀 판단 필요.
B-6 개선 보통
지정가 매도 예약 수량이 화면에 노출되지 않음
OrderService.createLimitOrder(SELL) / OrderExecutionService.executeSell
매수는 frozenBalance로 예약이 잔고에 명시적으로 드러나는 반면, 매도는 등록 시점에만 수량을 검증하고 Holding에 "매도 예약 중" 필드가 없다. 사용자가 보유종목 화면에서 "지금 팔 수 있는 수량"을 구분할 수 없다.
개선 방향(후보): HoldingResponse에 pendingSellQuantity 필드 추가해 노출.
팀원 C인증·조회·관리자 트랙
C-1 기능 공백 어려움
소셜 로그인 3사(카카오/네이버/구글)가 전부 Mock 더미 — 우선순위 최상위 후보
infra/oauth/KakaoOAuthClient·NaverOAuthClient·GoogleOAuthClient.getUserInfo()
실제 토큰 교환·프로필 API 호출 없이 code.hashCode()로 만든 가짜 이메일·닉네임을 반환한다. "실제 카카오 토큰 발급 및 사용자 프로필 API 조회 로직 구현부" TODO 주석이 그대로 남아있다. 지금 상태로는 소셜 로그인 버튼을 눌러도 실사용자 인증이 되지 않는다.
개선 방향(후보): Provider별 실제 토큰 발급 URL + 프로필 조회 URL 연동. DTO·인터페이스 골격은 이미 있어 구현체만 채우면 된다.
C-2 기능 공백 보통
회원 탈퇴(soft delete) 기능이 통째로 미구현
domain/user/entity/User.deactivate() — 호출부 0건, 탈퇴 엔드포인트 없음
schema.sql에 자식 테이블 8개 삭제 순서 + PII 익명화까지 설계돼 있고 User.deactivate() 엔티티 메서드도 있는데, 이를 오케스트레이션하는 서비스·컨트롤러가 없다. 사용자가 탈퇴할 방법이 API 레벨에 아예 없는 상태. AdminUserService 주석은 이미 탈퇴가 동작하는 것처럼 서술하고 있어 코드·주석 간 괴리도 있다.
개선 방향(후보): schema.sql에 명시된 순서(자식 테이블 삭제 → Redis 정리 → PII 익명화) 그대로 서비스 구현 + DELETE /api/users/me 추가.
C-3 개선 쉬움
이메일 인증코드 재발송에 쿨다운/레이트리밋 없음
AuthService.sendEmailCode() / RedisAuthCodeService.saveEmailCode()
같은 이메일로 연속 호출하면 매번 새 코드로 덮어쓰며 실제 메일이 계속 발송된다. 호출 횟수 제한이 없어 메일 스팸(폭탄) 벡터가 될 수 있다. Gemini 호출에는 이미 RedisRateLimiterService 패턴이 있어 대칭적으로 필요.
개선 방향(후보): auth:email_code:{email} 키가 살아있으면(TTL 남음) 재발송 거부 또는 최소 쿨다운 도입.
C-4 기능 공백 쉬움
관리자 액션(계정 정지, 문의 답변) 발생 시 사용자 알림이 안 감
AdminUserService.suspend() / AdminInquiryService.answerInquiry() / NotificationType
NotificationType에 SYSTEM/ORDER/AI/SIMULATION/NEWS만 있고 문의·계정상태변경용 타입이 없다. admin/auth/user 패키지 전체에서 NotificationService 호출이 0건 — 정지당하거나 문의 답변을 받아도 사용자는 다음 로그인 전까지 알 수 없다. 알림 인프라(STOMP 유니캐스팅)는 이미 있는데 관리자 도메인이 활용하지 않는 상태.
개선 방향(후보): NotificationType에 INQUIRY(또는 ACCOUNT) 추가 후 두 지점에서 notify() 호출 연결.
C-5 기능 공백 보통
비밀번호 변경/재설정 API 부재
UserController/UserService, AuthController — 해당 엔드포인트 없음
회원가입 시점 외에 비밀번호를 바꿀 경로가 코드에 없다. 로그인 상태에서 바꾸는 것도, 잊어버렸을 때 재설정하는 것도 둘 다 없다 — 실사용 서비스라면 필수 기능인데 완전히 비어있다. UserService.updateMyInfo()는 "loginId/비밀번호/투자성향은 이 API로 바꾸지 않는다"고 명시적으로 제외하고 있다.
개선 방향(후보): PATCH /api/users/me/password(현재 비번 확인 후 변경) + 기존 이메일 인증 인프라(RedisAuthCodeService) 재사용한 재설정 플로우.
C-6 개선 쉬움
알림 목록 조회 API에 페이지네이션 없음

LS증권 최신화 아키텍처
배경 재확인 — 코드 조사로 확인된 사실

지금 ls.mode 조건은 LsWebSocketClient에만 걸려 있다. LsAccessTokenProvider와 9개 REST 클라이언트는 클래스 주석에 "ls.mode와 무관하게 항상 동작해야 한다"고 의도적으로 설계돼 있다. 그런데 application-dev.yml은 "CI/테스트 및 LS 연동이 필요 없는 로컬 개발에서는..."이라는 주석과 함께 ls.mode 기본값을 mock으로 두고 있다 — 즉 dev/CI 환경은 애초에 "LS 연동 없이 돌린다"는 의도였는데, REST 클라이언트 9개는 이 의도와 무관하게 계속 실제 LS API를 호출해왔다는 뜻이다.

더 결정적으로, application-prod.yml에는 이미 mode: real # 추후 Mock 전환 브랜치에서 다시 바뀔 값이지만 지금은 실제 LS 연동을 사용한다는 주석이 있다. 즉 이번 변경은 이미 코드에 예고돼 있던 "Mock 전환"을 실제로 완성하는 작업이다 — production을 언젠가 ls.mode=mock으로 돌릴 계획이 이미 있었고, 그 mock의 실제 데이터 소스를 이번에 "로컬 파일"로 확정하는 것. A-1~A-7의 단계별 실행 순서는 위 "고도화 후보 — 담당자별" 보드의 팀원 A 카드를 참고하고, 아래는 그 단계들이 공통으로 참조하는 세부 규칙이다.

파일 조회 키 규칙 (제안 — 로컬 서버 구현 측과 합의 전)
LS 요청 바디는 전부 {trCd}InBlock 한 겹 규칙을 따른다(예: t1102InBlock, t1716InBlock). 즉 "무슨 데이터를 요청했는지"는 trCd + 그 안의 파라미터로 전부 결정되고, url(market-data-url 등)은 LS 쪽 라우팅일 뿐 파일 조회에는 의미가 없다. 파일 키는 trCd + 정렬된 파라미터 문자열로 만든다 — AiPlanningService.buildCacheKey()가 이미 쓰는 "파라미터를 키 기준으로 정렬해 문자열화"하는 원칙을 그대로 재사용한다. 
{ls.mock-data-path}/{trCd}/{key}.json
예) 현재가(t1102, shcode=005930)      → t1102/shcode=005930.json
예) 등락율상위(t1441, 파라미터 없음)   → t1441/default.json
파일 내용 = LS 실제 응답의 outBlock과 동일한 JSON 구조
  (각 parseXxx()가 지금 읽는 hname/price/sign 등 키를 그대로 채움 → 파싱 코드 무변경)
이 JSON 스키마가 로컬 시세 서버 쪽에 전달해야 할 "계약"이 된다. 9개 클라이언트가 쓰는 TR 코드 전체 목록은 application.yml의 ls.* 섹션 주석에 이미 정리돼 있다(t1102/t1716/t3401/t3202/t3341/t3521/t8428/t1441/t1444/t1452/ t1463/t1466/t1481/t1482/t1531/t1533/t1537 등) — 로컬 서버 착수 전 이 목록을 그대로 전달한다.
